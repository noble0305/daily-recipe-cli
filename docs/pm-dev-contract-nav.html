本文档是产品经理（PM）与开发团队之间关于「需求如何从想法走到可验收功能」的协作约定。 核心思路一句话：PM 定义需求（what / why），开发澄清与落地（how）——双方共用同一份 spec.md，验收标准只有一套。

本契约与团队现有的 Spec Kit 开发工作流 一一对应，是对它 「需求输入端」的补充：把原本”一句口头描述”升级为”PM 产出的结构化 spec 初稿”。

配套文件：PM 交付物模板（PM 填这份表）。

1. 目的与角色分工

1.1 要解决的问题

  • 需求靠口头/聊天传递，实现时才发现理解不一致，返工成本高。
  • PM 与开发各写各的文档，验收时标准对不上。
  • 需求变更没有书面轨迹，事后说不清”为什么这么做”。

1.2 角色分工

角色 管什么 交付物
PM what（做什么）与 why（为什么做）：业务价值、用户故事、优先级、验收标准 spec.md 初稿
开发 how（怎么做）：澄清歧义、技术方案、任务拆解、实现与测试 澄清结论、plan.md、tasks.md、代码、测试用例
双方 评审：确认 spec 的验收场景可执行、优先级合理 评审结论（PR 评审）

边界：PM 不写技术实现（语言、框架、数据格式），开发不替 PM 定义业务价值。 一句话需求（“做个 XX 功能”）不算交付物——必须落到 spec.md 模板。

2. PM 交付物格式

PM 产出 spec.md，结构复用 Spec Kit 的 spec 格式（模板见 docs/templates/pm-spec-template.md），至少包含以下章节。

2.1 必写章节

章节 内容要求 谁会用
功能背景（Input） 用一句话说清这个功能解决谁的什么痛点，背景是什么 开发理解动机
用户故事（User Stories） 每个故事含：场景标题、Priority（P1/P2/P3）、Why this priority 开发拆任务
验收场景（Acceptance Scenarios） 每条用 Given / When / Then 三句式；P1 故事必须全覆盖 开发转测试用例 + 验收
边界情况（Edge Cases） 明确写出：异常输入、空数据、重复操作、非交互场景的预期行为 开发写防御性代码
成功标准（Success Criteria） 可度量的结果（如”全程不超过 30 秒”），用于验收与复盘 双方验收

2.2 优先级定义

级别 含义 进入开发的条件
P1 本版本必须做，缺了功能不成立 必须 100% 完成并验收
P2 本版本应当做，有明确价值 至少一条验收场景通过后即可
P3 锦上添花，时间允许再做 可延后到下一版本

2.3 验收场景写作要求

  • 必须用 Given / When / Then 三句式，可直接翻译成测试用例。
  • P1 故事必须逐条覆盖验收场景；P2/P3 至少覆盖主流程。
  • 交互边界必须写：非交互场景（CI/管道/无人值守）下确认类操作怎么办、 非法输入怎么办、重复操作怎么办——这些在开发阶段最容易被忽视。

2.4 交互草稿（可选但鼓励）

对 UI 型功能，鼓励 PM 附交互草图/线框图（随手画即可）。纯逻辑或 CLI 型功能不强求， 不画不影响交付。

3. 衔接点约定

3.1 唯一入口：clarify

  • PM 的 spec.md 初稿不直接进入实现。开发/工作流先跑 /speckit-clarify 澄清歧义（开发向 PM 提问，PM 回答）。
  • 澄清结论必须回写进 spec.md，不留口头共识——“问过就忘”是需求跑偏的头号来源。
  • clarify 通过后，才进入 /speckit-plan → /speckit-tasks → /speckit-implement。

3.2 澄清时的责任

谁 责任
开发 逐条核对验收场景的可执行性；把发现的多解/冲突/遗漏提给 PM
PM 对歧义点给出确定结论；结论更新到 spec.md

原则：开发不替 PM 拍板业务语义，PM 不替开发决定技术取舍。

4. 评审与变更

4.1 评审

  • spec.md 初稿必须经过 PM + 开发 共同评审才能进入 plan 阶段（本仓库走 PR 评审）。
  • 评审人重点看：验收场景是否可执行（Given/When/Then 完整）、优先级是否合理、 边界情况是否覆盖。
  • 评审不通过 → 回到 clarify 修订，通过后重新提交评审。

4.2 需求变更

  • 任何需求变更必须回写 spec.md，走与初稿相同的评审流程。
  • 禁止”口头改需求 + 代码直接改”——变更没有书面轨迹等于没变更。
  • 变更评审通过后，按影响范围更新 tasks.md（新增/调整任务）再继续实现。
  • 用户可见行为变更同步追加 CHANGELOG.md（中文条目）。

5. 验收约定

  • 验收标准唯一来源 = spec.md 的验收场景，双方共用，不另立标准。
  • 开发：把每条验收场景转成测试用例（本项目为 pytest），保证测试覆盖。
  • PM：功能完成后，依据同一份验收场景做最终确认（P1 全覆盖，P2/P3 按约定范围）。
  • 验收不通过 → 缺陷清单回给开发，修复后重新验收；发现验收场景本身表述不清 → 走变更流程更新 spec.md。
