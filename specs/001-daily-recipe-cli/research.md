## 结论摘要

所有技术未知项已在 plan 阶段确定，无遗留 NEEDS CLARIFICATION。本文件记录关键设计决策、权衡与被否方案，作为后续实现与复盘依据。

## 关键决策与权衡

### 1. 用户数据目录：`~/.daily-recipe-cli/`

- **选择**：用户数据（`recipes.json`、`history.json`）放在用户主目录下的 `~/.daily-recipe-cli/`，包内捆绑 `default_recipes.json` 作为初始库，首次运行自动拷贝。
- **理由**：① 数据与代码分离——更新代码不覆盖用户食谱；② 多项目可复用同一套食谱；③ 符合 CLI 工具惯例。
- **被否方案**：数据放项目目录——升级/重装即丢数据；放系统配置目录（XDG）——macOS 上路径复杂，个人工具不必。

### 2. 随机种子策略：日期种子 + `--seed` 覆写

- **选择**：默认种子由「当天日期字符串」派生（如 `2026-08-15`），同一天重复运行得到相同候选（确定性，符合原则 III）；`--seed <值>` 显式覆写，用于测试与手动复现。
- **理由**：每日推荐天然按天稳定——早上看和晚上看结果一致，用户不会困惑；`--seed` 保证可测试性。
- **被否方案**：真随机（`random` 默认）——不可复现、不可测试；仅用户手动选择——丢失自动性。

### 3. 去重窗口：默认 7 天，`--days` 可调

- **选择**：候选生成时排除历史中最近 N 天（默认 7）已选中的菜；`recipe today --days 14` 等可调整。
- **理由**：带饭场景下 7 天轮换符合「一周不重样」的直觉；窗口可调覆盖口味偏好。
- **边界**：窗口内可选菜不足时，**放宽窗口**依次尝试（7→14→全库），并提示「已放宽去重窗口」；全库都不足才报「可选菜不足」。

### 4. 周规划：未来 5 个工作日 + 批内去重

- **选择**：`recipe week` 从下一个周一开始（当天起算，若今天非周一），生成 5 天菜单；天内选择满足去重窗口，天与天之间也互不重复（批内加一个「本周已选」集合）。
- **理由**：对应「周末批量规划」场景；批内去重避免一周内两天吃同菜。
- **被否方案**：连续 7 天含周末——用户周末可能不做带饭，需求明确是工作日。

### 5. 数据校验：手写校验函数，不引入第三方 schema 库

- **选择**：用标准库手写 `validate_recipe()` / `validate_history()`，对字段类型、必填项、重复名做检查，非法数据抛出带中文说明的异常。
- **理由**：符合「运行时零第三方依赖」原则；数据结构简单（两层 JSON），手写校验足够。
- **被否方案**：`jsonschema` 库——运行时新增依赖，收益对当前复杂度不成比例。

### 6. 今日已确定行为：重复提示 + `--force`

- **选择**：当天历史中已有「今日」记录时，`recipe today` 默认输出「今日已确定：X」，不再重新推荐；`recipe today --force` 跳过检查重新推荐（不覆盖已有记录，新的选择覆盖当天记录）。
- **理由**：避免误操作把当天决定冲掉；`--force` 给改主意留出口。

### 7. 新增 `recipe history` 命令（超出 FR 字面，属设计补充）

- **选择**：提供 `recipe history [--days N]` 查看历史记录。
- **理由**：FR-002 要求记录历史，但看不到历史则记录无意义；实现成本一行命令，是个人工具的自然需求。
- **说明**：此补充已在本 research 记录，后续 tasks 与 spec 修订保持一致（spec 补充对应 FR）。

## 风险与缓解

| 风险 | 缓解 |
|------|------|
| 用户手改 JSON 出错导致崩溃 | 全命令入口统一校验，非法数据给中文错误并指出字段 |
| 初始库不合口味导致工具弃用 | 初始库选大众化「带饭友好」菜（耐放、复热好），用户可 `recipe remove` 与 `recipe add` 快速调整 |
| 食谱库太小导致推荐重复 | 去重窗口放宽机制 + 明确提示可选菜不足 |
