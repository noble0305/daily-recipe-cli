# 功能规格：页面化访问（recipe-web-ui）

**Feature Branch**: `002-recipe-web-ui`

**Created**: 2026-08-15

**Status**: Draft

**Input**: User description: "我现在想将当前已有的功能设计到一个页面上去。可以通过页面进行访问查看和操作。应该如何设计"

## 用户场景与测试

### 用户故事 1 - 在页面上完成今日带饭决策（优先级 P1）

用户打开页面，看到今天的状态（是否已确定、候选菜），在页面上完成"查看候选 → 选中确认"的完整流程，不再需要记忆命令行参数。

**为什么是此优先级**: 今日推荐是产品的核心价值（宪法原则 I：只解决"今天带什么饭"）。页面化首先必须覆盖这条主链路，否则页面没有存在意义。

**独立测试**: 打开页面 → 展示候选菜 → 点击确认 → 页面显示"今日已确定"并出现在历史中。全程无需输入任何命令。

**验收场景**:

1. **Given** 食谱库中有 ≥3 道菜且今日未确定，**When** 用户打开页面并点击「今日推荐」，**Then** 页面展示 1~3 道候选菜及推荐理由（如避开最近 N 天）。
2. **Given** 页面展示候选菜，**When** 用户点击某道候选菜的「选它」按钮，**Then** 该菜与今日日期被记录到历史，页面切换为「今日已确定」状态并显示所选菜。
3. **Given** 今日已确定，**When** 用户再次打开页面或点击推荐，**Then** 页面提示今日已确定，并提供「重新推荐」入口（等价于 `--force`）。
4. **Given** 食谱库中可用菜不足 3 道，**When** 用户点击今日推荐，**Then** 页面提示「食谱库可选菜不足」并展示当前全部可用菜。

---

### 用户故事 2 - 在页面上管理食谱库 （优先级 P1）

用户在页面上查看全部食谱、按标签筛选、添加新食谱、删除已有食谱，操作结果即时反映在页面列表上。

**为什么是此优先级**: 食谱库是推荐的数据基础（宪法原则 II：数据可读、可维护）。没有页面化管理，用户仍需回到命令行维护数据。

**独立测试**: 在页面添加一道菜 → 列表立即出现；删除该菜 → 列表消失且历史记录不受影响。

**验收场景**:

1. **Given** 食谱库中存在多道菜，**When** 用户打开「食谱库」区域，**Then** 页面展示全部菜名、主要食材、标签与做法，并支持按标签筛选。
2. **Given** 页面处于食谱库视图，**When** 用户填写菜名/食材/标签/做法并提交，**Then** 新菜出现在列表中；菜名重复时提示「已存在」而非覆盖。
3. **Given** 页面展示某道菜，**When** 用户点击删除并确认，**Then** 该菜从食谱库移除，历史记录不受影响。

---

### 用户故事 3 - 在页面上规划一周菜单 （优先级 P2）

用户在页面上点击「周计划」，预览未来 5 个工作日的菜单，确认后一次性写入历史。

**为什么是此优先级**: 周批量规划是第二高频场景（宪法原则 I 的辅助价值），页面化后与 CLI 行为一致。

**独立测试**: 点击周计划 → 预览 5 天菜单 → 确认 → 历史中出现 5 条记录且互不重复。

**验收场景**:

1. **Given** 用户点击「周计划」，**When** 页面生成菜单，**Then** 展示下个周一起连续 5 个工作日的候选菜单，批内不重复，并避开去重窗口内的历史。
2. **Given** 页面展示周计划预览，**When** 用户点击「确认写入」，**Then** 5 天菜单一次性写入历史；点击「取消」则不写入。
3. **Given** 用户执行周计划时候选不足，**When** 页面生成失败，**Then** 页面给出中文提示与原因，不写入任何数据。

---

### 用户故事 4 - 在页面上查看历史记录 （优先级 P2）

用户在页面上查看最近吃过的菜，按日期倒序，可调整时间范围。

**为什么是此优先级**: 历史是去重与复盘的依据；页面化后用户可直观确认"最近吃了什么、为什么推荐避开这些"。

**独立测试**: 打开历史区域 → 按日期倒序展示最近 30 天记录（含来源标注）→ 调整范围后列表相应变化。

**验收场景**:

1. **Given** 页面处于历史视图，**When** 用户打开，**Then** 按日期倒序展示最近 N 天（默认 30）吃过的菜，标注来源（单日推荐或周计划）。
2. **Given** 历史记录存在多天数据，**When** 用户调整时间范围，**Then** 列表按所选范围刷新。

---

### 边界情况

- 数据文件缺失 / 损坏（非 JSON）：页面加载时给出中文错误提示与处理建议，不崩溃、不静默覆盖用户数据。
- 今日已确定后再次操作今日推荐：页面提示「今日已确定」，提供「重新推荐」入口（等价于 `--force`），且不重复写入。
- 食谱库为空：推荐/周计划给出友好提示与引导（先去添加食谱），页面不崩溃。
- 删除正在被历史引用的菜：历史记录不受影响（历史只存菜名快照）。
- 添加重名菜：提示「已存在」，不静默覆盖。
- 周计划生成失败（候选不足等）：不写入任何历史，页面给出中文原因提示。
- 页面刷新后状态保持：今日是否确定、已选菜、数据变化均持久化到数据文件，刷新不丢失。
- 并发/重复提交：连续快速点击「确认」不产生重复写入（今日同日期覆盖语义）。

## 需求

### 功能需求

- **FR-001**: 系统必须提供页面形式的总入口，聚合「今日」「食谱库」「周计划」「历史」四个视图，无需命令行即可完成全部现有功能。
- **FR-002**: 页面必须展示今日状态（未确定 / 已确定 + 所选菜），并提供「今日推荐」与「确认选择」操作，行为与 `recipe today` 一致（候选 1~3 道、默认避开 7 天、支持 `--force` 语义）。
- **FR-003**: 页面必须支持食谱库的查看（含标签筛选）、添加（菜名/食材/标签/做法）、删除，行为与 `recipe list/add/remove` 一致；重名提示「已存在」。
- **FR-004**: 页面必须支持周计划：生成并预览下个周一起 5 个工作日菜单，用户确认后一次性写入历史，行为与 `recipe week` 一致。
- **FR-005**: 页面必须支持历史查看：按日期倒序、默认最近 30 天、标注来源（单日推荐 / 周计划），行为与 `recipe history` 一致。
- **FR-006**: 页面必须支持标签过滤与去重窗口（默认 7 天）、随机种子等参数配置，行为与 CLI 对应参数一致且推荐可复现（同一种子 + 同一数据状态产出同一结果）。
- **FR-007**: 页面所有操作必须读写同一份数据文件（食谱库 + 历史），与 CLI 完全共享数据；页面与 CLI 任一方修改，另一方读取到最新状态。
- **FR-008**: 页面必须完全离线可用，无网络请求；数据仍为可手改的纯文本 JSON。
- **FR-009**: 页面在数据缺失 / 损坏 / 非法时必须给出清晰中文错误提示（含字段/位置），不崩溃、不静默覆盖。
- **FR-010**: 页面必须复用现有核心逻辑（推荐、去重、校验、历史读写），仅新增页面交互层，不得重复实现业务逻辑（已确认：直接复用现有 Python 核心模块）。

### 关键实体

- **页面视图（View）**: 页面上呈现的四大区域：今日 / 食谱库 / 周计划 / 历史，共享同一数据源。
- **操作（Action）**: 页面上对数据的交互动作（推荐 / 确认 / 添加 / 删除 / 规划 / 查看），与 CLI 命令一一对应。
- **数据文件（Data）**: 既有 `recipes.json` 与 `history.json`，页面与 CLI 共用（实体不变，页面不引入新数据格式）。

## 成功标准

### 可度量结果

- **SC-001**: 用户在页面上完成「今日推荐 → 确认选择」全程 ≤ 30 秒（不含思考时间），无需查看任何命令文档。
- **SC-002**: 页面与 CLI 操作同一数据文件时，任意一方修改后另一方立即读到最新状态（无缓存漂移）。
- **SC-003**: 页面完全离线可用；断网环境下全部四个视图可正常查看与操作。
- **SC-004**: 核心逻辑测试覆盖率不因页面化下降；现有 `uv run pytest` 全部通过且新增页面相关测试。
- **SC-005**: 首次打开页面即可完成一次完整今日推荐（含内置初始食谱库），无需任何配置。

## 假设

- 单用户、完全离线（宪法原则）；页面访问形态为「浏览器打开本地页面」：由 `recipe serve` 命令起一次性本机服务（仅监听 127.0.0.1）承载页面并自动打开浏览器，随用随起、浏览器关闭即退出，零安装、零常驻（调研结论：浏览器 CORS 安全限制使纯 file:// 页面无法读写本地 JSON，须经本地回环 HTTP 服务；详见 research.md）。
- 页面与 CLI 并存，互为补充：CLI 保留，页面是新增的访问入口，不替代命令行。
- 页面不引入新功能（YAGNI）：不加食材匹配、菜谱详情、外部 API 等 V1 之外能力（宪法原则 I）。
- 技术实现遵循宪法约束：Python 3.11+、运行时仅标准库、完全离线（具体实现由 plan 阶段决定，本 spec 不限定）。
- 数据契约不变：仍以 `contracts/data-schema.md` 为准，页面必须遵守同一校验与错误语义。
