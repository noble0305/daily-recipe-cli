# 快速验证指南：页面化访问（recipe-web-ui）

**日期**: 2026-08-15 | **规格**: [spec.md](./spec.md) | **API 契约**: [contracts/api.md](./contracts/api.md) | **数据模型**: [data-model.md](./data-model.md)

本指南是可运行的端到端验证场景，证明功能按规格工作。实现细节见 `tasks.md` 与实现阶段。

## 前置条件

- Python 3.11+，`uv` 已配置（`uv sync` 完成）
- 数据目录：默认 `~/.daily-recipe-cli/`，可用 `RECIPE_CLI_DIR` 覆写（测试用临时目录）
- 无网络要求（完全离线）

## 场景 1：启动页面并完成今日推荐（spec US1）

**步骤**:

```bash
uv run recipe serve
# 预期：自动打开浏览器，访问 http://127.0.0.1:<随机端口>/
```

**预期结果**:
1. 页面展示「今日」区域，显示未确定状态与「今日推荐」按钮。
2. 点击「今日推荐」→ 展示 1~3 道候选菜（含推荐理由，如「避开最近 7 天」）。
3. 点击某道菜的「选它」→ 页面切换为「今日已确定」，显示所选菜。
4. 关闭浏览器标签页 → `recipe serve` 进程自动退出（`/api/bye`），终端无残留进程。

**对照**: CLI `uv run recipe today` 对同一数据文件的行为与页面一致（spec SC-002 数据共享）。

## 场景 2：页面管理食谱库（spec US2）

**步骤**: 在页面「食谱库」区域操作。

**预期结果**:
1. 查看：展示全部菜名/食材/标签/做法，支持按标签筛选。
2. 添加：填写菜名/食材/标签/做法提交 → 列表立即出现新菜；重名提交 → 中文提示「已存在」。
3. 删除：点击删除并确认 → 菜从列表消失；`recipe list` 验证已移除，`recipe history` 验证历史不受影响。

## 场景 3：周计划预览与写入（spec US3）

**步骤**: 在页面「周计划」区域操作。

**预期结果**:
1. 点击「生成周计划」→ 预览下个周一起 5 个工作日的菜单，批内不重复。
2. 点击「确认写入」→ 5 天菜单一次性写入历史；`recipe history` 可查到 5 条来源为 `week` 的记录。
3. 重新生成并点「取消」→ 历史无新增。

## 场景 4：历史查看（spec US4）

**步骤**: 在页面「历史」区域操作。

**预期结果**:
1. 按日期倒序展示最近 30 天记录，标注来源（单日 `today` / 周计划 `week`）。
2. 调整时间范围（如 7 天）→ 列表按所选范围刷新。

## 场景 5：数据契约与边界（spec 边界情况）

**步骤**: 用 `RECIPE_CLI_DIR=/tmp/recipe-test` 指向一个破坏的数据目录再启动页面。

**预期结果**:
1. `recipes.json` 写为非法 JSON（如 `{`）→ 页面加载时展示中文错误「食谱库格式错误：……」，不崩溃、不覆盖。
2. 今日已确定后再次点「今日推荐」→ 提示「今日已确定」，提供「重新推荐」入口；确认重推后当日记录被覆盖（不重复新增）。
3. 食谱库为空 → 推荐提示「食谱库可选菜不足」，引导去添加食谱。
4. 页面刷新 → 今日状态与数据保持（从数据文件重新加载）。

## 验证命令汇总

```bash
uv run pytest                # 全部测试（含新增页面相关测试）
uv run recipe serve          # 启动页面（场景 1~4）
RECIPE_CLI_DIR=/tmp/rt uv run recipe serve   # 隔离数据目录跑边界场景（场景 5）
```
